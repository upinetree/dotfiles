# cross-review

Codex（別ベンダーのモデル）とサブエージェントは見落とす欠陥が重なりにくいので、同じ依頼文を両方に渡して独立にレビューさせる。依頼の一言から毎回組み立て直すと、独立性・根拠の要求・再レビューのどれかが抜けるため、手順をここに固定する。

## 1. 依頼文を作る

レビュー依頼の全文を scratchpad の Markdown ファイル（例: `review-<対象>.md`）に書き、両方のレビュアーにはそのファイルを読ませる。両者に同じ依頼が届き、Codex への受け渡しで引用符が崩れることもない。対象が複数あるときは共通部分を別ファイルにし、各対象のファイル冒頭で先に読むよう書く。

依頼文に入れるもの:

- 対象: リポジトリ、PR 番号やブランチ、レビューさせる差分の取り方（`git diff origin/<base>...HEAD` など）、意図を読むためのコミットメッセージや設計文書のパス。別ブランチなら `git fetch` してから worktree を切り、そのパスを作業ディレクトリとして書く（ローカルツリーを読ませると適用前の内容をレビューさせる）
- 背景: 差分から読めない前提。デプロイ先と頻度、本番の利用量、依存のバージョン、仕様の出典
- 観点: 番号付きで 2〜4 個。ユーザーが観点を挙げたらそれを使う（「仕様との整合」「バックエンド」など）。依存の挙動に結論が懸かるなら「記憶でなく該当タグの実ソースを読む」と書く
- 禁止: ファイルの編集・commit・push・PR へのコメントや投稿をしない。共有リソースを使うコマンド（DB を使うテスト、クラウドの API など）を実行させない場合は、その理由と一緒に書く
- 根拠の規則: 指摘ごとに file:line と該当行の引用、または実行したコマンドと出力を付ける。付かないものは「未検証の仮説」に分ける。「〜が残っていない」のような不在の主張には検索コマンドと範囲を書く。観点ごとに何も無ければ「指摘なし」と書き、何を調べたかを添える。最後に「確認できなかったこと」を書く
- 出力: 日本語。重大度順に「重大度 / file:line / 問題 / 根拠」。判断が分かれた点（迷った箇所と、どちらを採ったか）があれば別に挙げる

入れないもの: 自分の結論や懸念。先に渡すとレビュアーがそこへ寄り、独立レビューの意味が消える。自分の結論との突き合わせは戻った後に行う。

## 2. 並列に起動する

同じメッセージで 2 つの Agent を起動する（どちらも `run_in_background: true`）。

- Codex: `subagent_type: "codex:codex-rescue"`。このラッパーは依頼文から書き込みの要否・実行方式・前回の続きかどうかを推測し、修正を含むと読めば `--write` を、長い作業と読めばバックグラウンド実行を、続きの作業と読めば `--resume-last` を選ぶ。バックグラウンドを選ばれるとレビュー結果ではなくジョブ起動の 1 行しか返らないので、プロンプトに次をはっきり書く:
  - 読み取り専用のレビューで、`--write` を付けない
  - `--wait` を指定し、`--background` を付けない（フォアグラウンドで実行する）
  - `--fresh` を指定し、`--resume-last` を付けない
  - `--cwd <作業ディレクトリ>` と `--prompt-file <依頼文ファイルの絶対パス>` を付けて companion の `task` に渡す。プロンプトには `<…>` を残さず実パスを書く（`--cwd` に実在しないパスを渡すと即座に失敗し、「Codex CLI が入っていない」という原因と違うエラーになる）。Codex は `--cwd` を含む git リポジトリのルートで動き、指定しないとラッパーのシェルの cwd が基準になる。`--prompt-file` の相対パスは `--cwd` を基準に解決される
  - 本文は「読み取り専用で、<依頼文ファイルの絶対パス> を読んでそのとおりにレビューし、日本語で報告する」の 1 文にする。`--prompt-file` が付けば companion がファイルを読んで中身だけを Codex に渡し、本文は捨てられる。ラッパーがフラグを付けずに本文ごと転送した場合でも、Codex が自分でファイルを読みに行ける。どちらの経路でも、読み取り専用と日本語の指定は依頼文ファイル側に書いてあることが前提になる
- サブエージェント: `subagent_type: "general-purpose"`。ユーザーがモデルを指定したら `model` に渡す（例: `"fable"`）。プロンプトは依頼文ファイルを読んでそのとおりにレビューするよう書き、禁止事項を重ねて書く

起動した 2 体の agentId と依頼文ファイルのパスを控えておく（再レビューで使う）。

## 3. 戻った指摘を検証して示す

Codex の結果は中身を確かめてから読む。次のどれかなら、レビューは届いていない。「指摘なし」と読まずにユーザーへ伝え、Codex をやり直すか、片方だけのレビューで進めるかを確かめる。

- 空の結果（ラッパーは Codex を起動できないと何も返さない）
- エラーの出力
- `started in the background as <jobId>` のようなジョブ起動の 1 行。結果は Bash で取り出す。companion は `~/.claude/plugins/cache/openai-codex/codex/<版>/scripts/codex-companion.mjs` にある。まず `status <jobId> --wait --cwd <作業ディレクトリ>` で終わるのを待ち（実行中に `result` を呼ぶと失敗する）、まだ queued か running と出たら同じコマンドを繰り返す。待ちの上限は既定で 240 秒なので、Bash の `timeout` は 300000 にする。終わったら `result <jobId> --cwd <作業ディレクトリ>` で取り出す。ジョブが見つからなければ、ラッパーが `--cwd` を付けなかったか別のパスを渡しているので、下のジョブの記録でそのジョブの `workspaceRoot` を確かめ、その値を `--cwd` にして実行し直す。`/codex:result` はモデルから呼べず、ユーザーが引数に `--cwd` を書かない限りセッションの cwd で探すので、worktree のジョブを見つけられない
- 依頼文ファイルを読めなかったという報告。`--prompt-file` が正しく渡って companion が読めた場合は、依頼文の受け渡しは Codex の sandbox に左右されない。ラッパーがフラグを落として Codex が自分で読みに行った場合は、ファイルが無いときのほか、作業ディレクトリの外を読み取り専用の sandbox で読めないときにも起きうる（後者は確かめていない）

空の結果やエラーの原因を調べるときは、まず自分がラッパーへのプロンプトに書いた `--cwd` と `--prompt-file` のパスが実在するかを確かめる。それでも分からなければ、ジョブの記録を読む。記録は `$CLAUDE_PLUGIN_DATA/state/*/jobs/*.json`（未設定なら一時ディレクトリの `codex-companion/*/jobs/*.json`）にある。`ls -t` でフォルダをまたいで新しい順に並べ、`sessionId` が `$CODEX_COMPANION_SESSION_ID` と同じで、`createdAt`（UTC）が今回の起動時刻に合うものを候補にする。並列に複数の Codex を起こして候補が複数あれば `summary`（依頼文の冒頭）で見分け、見分けられなければ原因を確定しない。特定できた記録の `errorMessage` を読む。今回の時刻の記録が無いのは、companion がジョブを作る前に失敗したか、ラッパーが companion を呼べていない場合で、一番新しい記録を今回の失敗とみなさない。記録の `workspaceRoot` は渡した `--cwd` を含むリポジトリのルートになるはずなので、食い違っていればラッパーがパスを落としたか変えた手がかりになる

指摘は一つずつ自分で裏を取る（該当行を開く、コマンドを実行する）。「反証あり」にするのは、該当行の引用や不変条件のように示せる反証があるときだけで、示せなければ「確認できず」にする。両者で結論が割れたら、多数決にせず一次資料を読んで決める。示すときは番号付きの表にし、指摘・出どころ（Codex / サブエージェント / 両方）・裏取りの結果（確認済み / 反証あり / 確認できず）・対応の推奨を並べる。直すかどうかはユーザーに委ねる。

## 4. 直したら再レビューする

指摘を受けて直したら、報告・commit・push より前に再レビューする。省くのはユーザーが不要と明示したときだけで、省いたら報告にそう書く。

- サブエージェント: 控えた agentId に SendMessage で再開する
- Codex: 2 節と同じ書き方（`--fresh` を含む）で、新しい Codex を起動する。再レビューの依頼は前回の続きに見えるので、`--fresh` を書かないとラッパーが `--resume-last` を足しうる。`--resume-last` は、同じリポジトリで現在の Claude セッションが最後に終えた Codex タスクのスレッドを再開し、同じセッションで別の Codex タスクが動いていると失敗する。並列に複数のレビューを走らせた後や他の Codex 作業の後では、意図と違うスレッドにつながる

再レビューの依頼文は新しいファイルに書く。元の依頼文ファイルのパスを示して、禁止事項・根拠の規則・出力形式はそれに従うよう書き（新しく起こした Codex は前回の文脈を持たない）、前回の指摘それぞれと対応内容、修正の差分の取り方（`git show <sha>` など）を足す。そのうえで次の 2 点を判定させる。

1. 前回の指摘ごとに、解消 / 未解消 / 部分的、とその根拠
2. 修正で新しく入った問題が無いか（コメントや文書の正確さを含む）

2 を書かないと、レビュアーは元の指摘の確認だけで終わる。再レビューでまた指摘が出たら 3 と 4 を繰り返す。
