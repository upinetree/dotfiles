# compact-prep

## compaction 後にこの本文が見えている場合

このスキルの本文は compaction 後にも再注入される。分岐は「ユーザーがいまのターンでこのスキルを呼んだか」で決める。

- **今回のターンで呼ばれた**（2 回目以降の compaction 準備を含む）: 以下の手順を実行する
- **呼ばれておらず、本文だけが見えている**: 手順を実行しない。引き継ぎファイル（`compact-handoff` で始まる名前）を Read し、書かれた「次の手順」から作業を再開する（ユーザーの直近の発言に別の依頼があれば、そちらを優先する）。パスが会話に無ければ、scratchpad の `compact-handoff.md` があるかを確かめて、あれば読む

## 目的と射程

`/compact` の要約は損失がある。何が重要かを汎用の基準で決めるので、採らなかった案、検証の証拠、会話の途中で付いた条件が落ちやすい。そこで、残したい状態を先にファイルへ書き出し、compaction 後にそれを読み直させる。

- 射程は **Claude Code の同じセッション内での手動 compaction**。`--resume` での再開も同じセッションとして扱える
- 再起動後や別のセッションで読み直す予定があるとユーザーが言った場合は、消えない置き場所（リポジトリの `tmp/` など）にするかを確かめてから書く。名前は `$TMPDIR` の場合と同じ形式にし、gitignore されていない場所ならその旨をユーザーに伝える

## 手順

### 1. 会話を棚卸しする

会話全体を読み直し、次の観点で拾う。該当が無い観点は書かない。

- **目的と射程**: ユーザーの依頼をユーザー自身の言葉で書く。途中で付いた条件・除外（「〜は一旦対処なしで OK」など）も書く
- **決定**: 何を決めたか、なぜか、採らなかった案とその理由
- **作業の状態**: 完了・検証済み / 進行中 / 未着手 に分ける。完了には根拠（コミット SHA、PR 番号、実行コマンドと終了コード、実測値）を添える。根拠が無いものは「未検証」と書く
- **仮説**: 仮説ごとに状態（未検証 / 支持 / 反証）と、その根拠になったデータ
- **このタスク限りの訂正・フィードバック**: このセッションで受けた指摘のうち、この作業にだけ効くもの（次のセッションでも効くものは手順 3 で memory へ）
- **未解決の問い**: ユーザーの回答待ちのもの、判断を保留したもの
- **次の手順**: 次のターンでそのまま実行できる粒度で書く（コマンド、ファイルパス、確認すること）
- **参照先**: 触ったファイル、ブランチ、worktree、PR・issue、Artifact や Notion の URL、バックグラウンドで走っているジョブやエージェント

リポジトリや外部に正本があるもの（git log、PR 本文、ファイルの中身）は写さず、場所だけ書く。逐語で写すのは、ユーザーの発言・付いた条件・実測値に限る。

### 2. 現在の状態を実測する

書く直前に、少なくとも次を実際に確かめる。

- `git status --short` と現在のブランチ（未コミットの変更があればそのパス。git リポジトリでなければ省く）
- 実行中のバックグラウンドジョブ・サブエージェント

実測しなかった項目は「会話時点の値」と注記する。

### 3. memory は長く使う事実だけ

memory には、この会話の外でも使う事実（ユーザーの方針、プロジェクトの制約、外部リソースの場所、次のセッションでも効く訂正）だけを書く。セッション内だけの作業状態は引き継ぎファイルに書き、memory には入れない。該当するものが無ければ memory は触らない。

### 4. 外向きの操作はしない

この準備の一環として commit・push・stash、PR やコメントの投稿はしない。未コミットの変更は手順 2 で確かめたとおり引き継ぎファイルに書く。

### 5. 引き継ぎファイルを最後に書く

compaction 直後には、そのセッションで読んだか編集したファイルのうち更新が新しいものから最大 5 件が自動で再読込される。5,000 トークンを超えるファイルは中身なしのパス参照になる。この再読込に乗せるため、次を守る。

- **このスキルで触る最後のファイルにする**。書いた後に他のファイルを編集しない
- 5,000 トークン以内に収める。日本語 1 字あたりのトークン数は確かめていないので余裕を取り、`wc -m` で約 3,000 字を上限の目安にする
- 書く → `wc -m` で測る → 超えたら正本が別にあるものを場所だけに削って測り直す → 最後に一度 Read して内容を確かめる、の順で進める（Write だけで再読込の対象になるかは未確認なので、Read で「読んだファイル」にもしておく）

置き場所とファイル名:

- system prompt にある scratchpad ディレクトリの `compact-handoff.md`（絶対パス）。scratchpad はセッションごとに分かれている
- scratchpad が無い環境では `$TMPDIR/compact-handoff-<repo名>-<YYYYMMDD-HHMM>.md`（`<repo名>` は git リポジトリでなければ cwd のディレクトリ名）。`$TMPDIR` は他のセッションと共有なので、名前を固定しない

書き方:

- 冒頭に、書いた日時・cwd・ブランチを入れる。中の数値・状態は「その時点の値」であることを明記する
- 既存ファイルを更新するかは置き場所で決める
  - scratchpad: セッションごとに分かれているので、既存の `compact-handoff.md` は必ずこのセッションのもの。あれば常に読んでから更新する
  - `$TMPDIR` や `tmp/`: このセッションで前に書いたファイルのパスが会話（要約を含む）にある場合だけ、読んでから更新する。無ければ他の既存ファイルには手を出さず、新しい名前で作る
- 更新するときは、古くなった項目を直し、解決済みの項目は再発防止に要るものだけ 1 行で残して他は削る
- 文脈を持たない読み手が読む前提で書く。「さっきの件」のような会話内の指示語を使わない
- 事実（実測・出力で確かめたもの）と主張を区別して書く。主張には、推測、サブエージェントや他者の報告、**以前の compaction の要約にしか残っていない内容**を含める

### 6. 貼る 2 行を返す

ユーザーがそのまま貼れる 2 つを、それぞれコードブロックで返す。

compaction 前に貼る 1 行:

```
/compact 要約の冒頭に「作業を再開する前に <絶対パス> を Read する」と明記する。要約では次を優先して残す: <このセッション固有の 2〜4 項目>
```

- 優先項目は、ファイルに書き切れない会話の流れのうち、このセッションで落ちると困るものを選ぶ（例: 「ユーザーが却下した案 X とその理由」「仮説 B は反証済みであること」）。汎用の項目（「未完了タスク」など）は既定の要約でも拾われるので入れない
- 引数は 1 行に収める

compaction 後に貼る 1 行（要約や自動再読込が効かなかった場合の保険）:

```
<絶対パス> を読んでから作業を再開して
```

最後に、memory に書いたものがあればその一覧を短く添える。
