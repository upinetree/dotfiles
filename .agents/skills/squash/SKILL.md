# Squash

このブランチのコミットを1つにまとめ（squash）、コードから読み取れない why を中心にコミットメッセージを書いてください。

## 手順

1. `BASE` を特定する
   - 引数でベースブランチが指定された場合はそれを使う
   - それ以外は `git rev-parse --abbrev-ref @{upstream} 2>/dev/null || git rev-parse --abbrev-ref origin/HEAD` で取得する
2. `git log`, `git diff --stat`, `git diff` でブランチの変更全体を把握する
3. `git reset --soft $(git merge-base HEAD $BASE)` でコミットを soft reset する
4. 元コミットの本文（と PR 本文）から why の候補を拾い、下の「why の選び方」で残すものを決める
5. 残した why で Conventional Commits 形式のコミットメッセージを作成する
6. `git commit -m "..."` でコミットする

## why の選び方

元コミットの本文は why の**候補**であって、そのまま載せる素材ではない。各コミットの why はそのコミットの小さな diff に向けて書かれたもので、squash 後の 1 つの diff には、同じ why を説明するコメント・ADR・spec が一緒に入っていることが多い。ユーザー global CLAUDE.md「コミットメッセージ」の判定基準（消したとき diff から読み取れなくなる情報があるか）でいう diff には、そのコメントや、同じブランチで足した ADR も含まれる（ほかの場所にある文書の扱いは項目 2）。だから候補を全部つなぐと、コメントの再掲で長くなる。

候補を 1 つずつ次の順に当て、当たったものを落とす。

1. **最終状態に残っていない経緯**: このブランチの途中のコミットで入れて後で消した実装・暫定値・仮置きの説明。ブランチより前からあった状態（前の PR の仮置きなど）は対象外で、それを改めたことは変更が要る理由として残る
2. **固定された場所にすでに書いてある why**: 候補の要点の語で、squash 後の diff と作業ツリーの両方を探す（`git diff $BASE...HEAD | grep -n <語>`、`git grep -n <語>`。ADR はブランチより前からあることも多い。作業ツリーで見つかったものは、このコミットの diff か既定ブランチにあるかを確かめる。PR を積んでいるときの親のブランチにしか無いものは、まだ固定されていない。別のリポジトリの文書は `git -C <repo> fetch` のあと `git -C <repo> grep -n <語> origin/<既定ブランチ>` で、その既定ブランチにあるかを確かめる）。固定された場所とは、このコミットの diff の中（コード中の NOTE / TODO、spec の説明、同じブランチで足した ADR）と、既定ブランチにマージ済みの文書のこと。issue・PR の本文や Slack はいつでも書き換えられ、レビューも通らないので、固定された場所に数えない（リンク先としては使う）。コミットの diff は後から変わらないので、diff 内のコメントにある why は、コメントが後で消えてもコミットと一緒に残る。固定された場所のどれか 1 つに同じ内容があれば削る（ほかにマージ前の ADR などにもあってよい）。コミットにも書くと二重管理になり、片方だけ古くなる。照らし合わせは要点ごとに行い、コメントにあるのが「なぜこの形か」だけなら、きっかけ（何が起きて気づいたか）は残す。固定された ADR の決定に依っているなら、説明は削って番号だけを残す（マージ前の ADR は下の例外）。コードに `@see` があっても番号は残す（説明の重複ではなくリンクで、blame で来た人がコードを開かずに辿れる）
   - 置き場所がまだ固定されていない why（別のリポジトリでマージ前の ADR、まだ作られていない別の変更への申し送り）は落とさず、要点を 1 文に縮めて PR・issue へのリンクを添える。マージ前に書き換わったり、マージされずに終わったりすると、コミットの指す先が当時の why とずれるか、消えるため。要点は「何を決めたか・何をどこが持つか」までにし、値や詳細はリンク先に任せる（写すと食い違う元が増える）。「マージ前」のような今だけの状態は書かず、リンクだけにする（コミットは長く残り、状態はすぐ古くなる）
3. **決定の経緯**: いつ・誰が決めたか、前の決定から何を改めたか。経緯は ADR や GitHub・Slack などの議論に残るものなので、本文には書かず、要るならその場所へのリンクだけを置く
4. **what**: 「〜のケースを足した」「件数を分けて引く」のような変更の言い換え。文の中に why が混ざっていれば why の部分だけ残す

背景が込み入っていて 1 行目だけでは何が変わったのかを掴めないときは、本文の冒頭に変更全体の概要を 1〜2 文置く。置くかどうかは diff の大きさではなく背景の複雑さで決める。ここでいう複雑さは変更後の挙動が 1 行目に収まりきらない度合いで、項目 2・3 で落とした why（決定の経緯など）の込み入り具合は数えない。判定は 1 行目だけで行い、後に続く文は当てにしない。1 行目だけで変更後の挙動を掴めるなら、概要は 1 行目の言い直しになるので置かない。変更前の状態は理由の文が受け持つので、判定に入れない。概要は「何ができるようになったか・挙動がどう変わったか」を書くもので、ファイル・クラス・個々の変更を並べるものではない（並べ始めたら項目 4 に当たる）。コメントの多いコードでは why がほとんど落ちて本文が概要と理由の置き場所だけになることもあるが、それでよい。

概要のほかに落ちずに残るのは、たいてい次のもの: この変更が要る理由（問題・きっかけ）、その挙動にした理由のうち固定された場所に無いもの（置き場所がまだ固定されていないものは要点だけ）、テスト設計の意図（どの誤実装と結果が分かれるように置いたか）、ADR・issue・議論へのリンク。

特定の行の実装上の理由（境界値や単位の扱いなど）で、固定された場所に無いものは残してよい。ただしコミットよりコメントに置くべき内容なら、squash ではコードを変えず、コメントへ移す案として作業後にユーザーへ伝える。

書き終えたら、本文の長さを元コミットの本文の合計と比べる。ほとんど縮んでいなければ、選別が効かずに連結しただけのことが多いので、候補を当て直す。長さは元コミットの数ではなく、残った why の量で決まる。

## コミットメッセージの方針

書き方の規約（1 行目の形式、why を主節に置く、書かないもの、見出しの付け方、PR 本文との分担）はユーザー global CLAUDE.md「コミットメッセージ」に従う。ここには squash に固有のことだけを書く。本文は why だけという規約の例外は、冒頭の概要（「why の選び方」）だけ。根拠へのリンクや ADR の番号は、規約が why に含める根拠なので例外ではない。

- 本文は squash 後の差分が大きいぶん、what を書き始めると diff の目録になりやすい
- 元コミットのメッセージを機械的に連結しない。実装途中の暫定表現や rebase で混入した `# Conflicts:` 行は捨て、最終状態の事実として書き直す
- PR を既に作っている場合、PR 本文にしか無い why はコミット側へ移す（blame から辿れるのはコミット）。移すときも「why の選び方」を通す
- フッター: Claude 由来のものとそれ以外で扱いを分ける
  - **Claude 由来の trailer**（`Claude-Session:`、`Co-Authored-By: Claude <...>`、`🤖 Generated with Claude Code` など）は元コミットから引き継がない。付与するかどうかは squash 後のコミット作成時に `~/.claude/settings.json` の `attribution` 設定（`commit` / `sessionUrl`）に従って決まるので、ここで手動コピーしたり `git commit -m` の本文に書き足したりしない
  - **それ以外の trailer**（人間による `Signed-off-by`、`Reviewed-by`、Issue 参照など）は `git log $BASE..HEAD` で元コミットを確認し、使われていれば引き継ぐ。複数あれば重複を除いてまとめる
  - 引き継ぐべき trailer が無ければ付与しない
