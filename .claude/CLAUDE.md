# ユーザーローカル CLAUDE.md（全プロジェクト共通）

実体は `~/.dotfiles/.claude/CLAUDE.md`、`~/.claude/CLAUDE.md` から symlink される。編集はこの dotfiles 側で行う。このファイルは `~/.codex/AGENTS.md` からも symlink され、Codex のグローバルルールを兼ねる（二重管理しない）。

## Claude の設定・hooks・skills を変更するとき

`~/.claude`・`~/.agents`・`~/.codex` 配下の設定は dotfiles からの symlink である（`~/.dotfiles/scripts/link.sh` の `DOTFILE_PAIRS`、`make link` で適用）。

- `~/.claude/settings.json` → `~/.dotfiles/.claude/settings.json`
- `~/.claude/hooks` → `~/.dotfiles/.claude/hooks`（Codex の hooks.json もここのスクリプトを参照する）
- `~/.agents/skills/<name>` と `~/.claude/skills/<name>` → いずれも `~/.dotfiles/.agents/skills/<name>`（ディレクトリ単位で自動 link。正本はクロスエージェント標準の `.agents/skills`。Claude Code は `~/.claude/skills` しか読まないため橋渡し link も張る）
- `~/.claude/CLAUDE.md` → `~/.dotfiles/.claude/CLAUDE.md`
- `~/.codex/AGENTS.md` → `~/.dotfiles/.claude/CLAUDE.md`（Codex 用。実体は CLAUDE.md と共有）
- `~/.codex/hooks.json` → `~/.dotfiles/.codex/hooks.json`（hook の配線は settings.json と重複して持つしかない。hook の追加・削除・matcher 変更時は両ファイルを揃える）

変更は **dotfiles 側の実体を編集**し、`~/.dotfiles` でコミットする。`~/.claude`・`~/.agents`・`~/.codex` 側を直接編集しない。

対象が symlink ではなく実ファイルになっていたら symlink が壊れている（Claude Code が設定を直接書き換えると起きうる）。`make link`（または該当 1 本を貼り直し）で復旧してから編集し、内容が分岐した 2 コピーを残さない。

## Bash コマンド実行の作法

permission classifier はコマンドの複合度と依頼文脈との乖離に反応して拒否する。

- 1コマンド1目的で分割する。書き込み系を `&&` やパイプで連結しない。`cd A && B` は `make -C` / `git -C` で代替する
- `rm` は拒否される前提で組む。untracked ファイルは `git clean -f <path>`、それ以外は /tmp へ mv か別名作成で回避する
- 権限拒否されたら同じ形でリトライしない。どこまで実行されたかを確認し、分割・依頼文脈の明示・ユーザーによる実行（`!`）や allowlist 追加の案内に切り替える。allowlist 拡張の提案は曖昧な範囲でなく具体的なコマンドの列挙で行う
- ファイル編集に `sed -i` を使わず Edit ツールを使う。GNU/BSD 差で `-i ''` がエラーを出しつつ後続ファイル引数は処理される（部分適用）ため、「エラー = 未実行」と誤認して再実行すると二重適用になる
- ファイルへの `>` リダイレクトを使わない。zsh の noclobber で silent fail し、古い内容が残ったまま「検証成功」に見える事故が再発している。ファイル生成・上書きは Write ツールか python3 の `open()`。やむを得ずシェルで上書きする場合は `>|` を使い、直後に内容を検証する

## git 作業規律

- `git commit -a` / `-am` を使わない。対象ファイルを明示して `git add <path>` し、コミット前に `git diff --staged` でステージ内容を確認する。ユーザーが同じツリーを並行編集していることがあり、未コミット変更や無関係差分を巻き込む事故が再発している
- レビューを受けた後の修正は `--amend` + force-push で畳まず、新しいコミットとして積む。squash が要るならレビュー完了後かマージ時に委ねる（詳細は [依頼の境界と不可逆操作](#依頼の境界と不可逆操作)）

## コミットメッセージ

判定基準は [コメントの抽象度](#コメントの抽象度) と同じ: **その記述を消したとき、diff から読み取れなくなる情報があるか**。無ければ書かない。diff は常にメッセージの隣にあるので、what の再記述は情報量がゼロで、変更のたびに片方だけ古くなる。

- 1 行目は what でよい（`<type>[scope]: <description>`）。ここは `git log --oneline` の索引として機能する
- 本文は why だけで構成する: なぜ必要だったか（問題・きっかけ・発端になった評価や指摘）、なぜこの形にしたか（制約・採らなかった案）、diff に現れない前提・依存・波及、根拠（ADR・issue・PR・相談スレッド）
- **why を主節に置く。** what を主節にして why を従属節へ落とすと（「X を新設した。Y のためである」）、読み手は what の羅列として読み飛ばす。「Y のため X にした」の順で書く
- 書かない: 変更したファイル・クラス・メソッドの列挙、diff の言い換え（「〜を追加」「〜にリネーム」）、シンボルやフィールド名の網羅列挙、「テストを追加した」という事実そのもの（テスト設計の意図は書く）
- diff の構造を見出しでミラーしない（「構成:」「スキーマ / テスト:」のような節分けは what の目録になりやすい）。分けるなら why の単位で分ける
- 長さは why の量で決まる。why が無い変更（機械的追従・生成物の更新・フォーマット）は 1 行で終える
- PR 本文との分担: PR 本文はレビュアー向けで「やったこと・やらなかったこと・確認手順」を含めてよい。コミットメッセージは将来 `git log` / `git blame` でその行に到達した人向け。**PR 本文にしか無い why を残さない**（PR は blame から辿りにくく、squash すると本文の記述も履歴から消える）

## 依頼の境界と不可逆操作

実行前に「戻せるか」を見積もる。線引きは「重要か / 些細か」ではなく**可逆か / 不可逆か**で引く。戻せる操作（ローカル編集、rebase、ブランチ操作）は判断で進めてよい。戻せない操作は、依頼に明示されていない限り実行しない。

- **相手に通知が飛ぶ操作は、明示的に依頼されたときだけ実行する。**「読んで」「直して」「調べて」に、返信・コメント・投稿は含まれない
- 送信済みの通知は撤回できない。コメントの削除は表示を消すだけで、メール / Slack に飛んだ通知と相手の読了は巻き戻らない。**外向き操作の可逆性は「UI 上で消せるか」では測れない**
- 同種の操作を直前に承認されていても、それは当該操作への承認であって次回への包括承認ではない
- git の履歴操作はレビューへの影響で二層に分かれる。**rebase は SHA を替えるがレビュー対象の内容は保つ（再アンカーされうる）のに対し、amend はレビューされた内容そのものを書き換える。** 「履歴を書き換える操作」と一括りにして、許容できるものまで禁じない。レビュー後の修正は新コミットで積む（main への追従 rebase はこの制約の対象外）
- **ユーザーの一度の整頓要求を、継続的な制約として拡大解釈しない。**「squash しよかな」はその時点の整頓であって「以後 1 commit を維持せよ」ではない
- 外部レビューの指摘が自作物の外（他 issue・他ファイル）へ波及しても、反映は依頼スコープに厳密に絞る。スコープ外は「記録価値のある指摘」として文書化に留める

## 前提の再確認

状況が動いたら、承認済みのタスクでも前提を洗い直してから着手する。

- 大きな rebase・base 更新・PR マージ・コード凍結の後は、plan が置いた前提（実装済みか未着手か）、従っていた規約（採番方式など）、リポジトリ内ツールのパス（ディレクトリ移設）を再確認する。コンフリクトゼロ・CI green のまま前提だけが腐る
- 冒頭の環境スナップショット（`git status`・git リポジトリか否か・ローカルツリーの状態）に矛盾があれば、本題より先に原因を診断する。未修復のまま checkout / commit すると誤った working tree に書き込む
- ユーザーが前提付きで提案してきたら（「実データが入っていなければ」）、その前提自体を裏取りする。前提が崩れて結論が確定することも、前提そのものが不要になることもある
- 自分が前ターンに引いた境界線・主張も、判断評価のときは同じ俎上に載せて再評価する

## レビューの多層運用

- 異なる観点のレビューは検出する欠陥集合がほとんど重ならない。修正はそれ自体が新たな変更なので、**修正フェーズで持ち込んだ欠陥を拾う層を必ず置く**
- 再レビューは新規起動より SendMessage で再開する（前回指摘の解消を判定できるのは指摘した本人）。依頼文に「新たな問題の混入確認」も明示してアンカリングを防ぐ
- 検証エージェントには「REFUTED は実際の行の引用・不変条件の提示など**構築可能な反証がある場合に限る**」と明示する。もっともらしい指摘の潰しすぎを防ぎつつ、全候補に根拠を付けられる
- finding を報告する側にも同じ強度の根拠を要求する。各指摘に file:line の引用か、発火させたコマンドと出力を添えさせ、付かないものは本報告から外して別枠（未検証仮説）に落とす。verifier 側だけを縛ると、潰しすぎ防止の規律が過剰主張を通す穴になる
- 「初めて〜になる」「ガードが無い」のような不在・初出の主張は、grep / git log の実行結果を根拠に添えない限り書かない。不在証明は検索範囲を示さないと成立しない
- 並列 finder の結論が矛盾したら、多数決や要約の再読で決めない。該当ライブラリの実ソースをバージョン固定で取得して読み、確定事実を共有ファイルで後続の verifier に渡す（矛盾した前提から出発する finding が消える）
- 独立レビューは自分の検出器の漏れ（スキャン対象集合の除外ミスなど）を見つける。同じ文脈で作業する自分では気づけない
- 指摘は検証コストで三層に仕分ける（即断可能 / 一次資料で裏取り可能 / 裏取り手段なし）。レビュー依頼の出力形式に「確認できなかったこと」の明示を入れる
- レビュー対象が別ブランチなら fetch して worktree を切り、そのパスを渡す。ローカルツリーを読ませると適用前のコードをレビューさせることになる

## サブエージェントの待ち方

harness が追跡するサブエージェント・バックグラウンドジョブは完了時に自分が再呼び出しされる。完了確認のための短間隔 wakeup は情報を増やさず wall-clock とトークンだけ増やす。

- 待ちを目的に ScheduleWakeup を短間隔（〜300s）で置かない。ハングや通知取りこぼしに備える fallback は 1200s 以上にする
- 待っている間に placeholder のエージェントを起こさない。無効な wakeup が stale notification として戻り、打ち消しにさらにターンを使う
- 外部状態（CI・デプロイ・リモートキュー）を待つときだけは、その状態が変わる速さに合わせて間隔を決める

## 検証の証拠主義

- 完了報告（自分・サブエージェントとも）は成果物の実在（コミット・ファイル・API 応答・transcript の tool_use）で検証してから伝える。サブエージェントの返答テキストだけを根拠にしない
- lint・構文チェック・通常テストの green は failure-only（失敗時のみ走る）コードの検証にならない。レアパスは一度実発火させて実ログで確認する
- 仮説は突き合わせ可能な実データ（時刻・ID・実測値）で確定させる。症状の一致だけで同根と断定しない
- 「0 件」「green」を報告する前に測定器を検証する。検出器・検証スクリプトは既知の陽性ケースで一度発火させ、否定的証拠（0 件・該当なし）には同じ手法で非ゼロが出る対照を添える。指標がきれいに 0 になったら、対象が直ったのか測定器が数えていないのかを区別する
- 「0 件になった」を主張するときは陽性対照を同一実行内に置く。別対象の件数が前後で不変であることを示せれば測定漏れを排除できる。対照は用意しなくても同じ実行に混ざっているものを使えることがある
- lint・test 系コマンドの合否は出力でなく終了コードで判定する（`; echo "EXIT=$?"` を付け、パイプ経由を避け、値が空でないことまで確認する）
- green の読み違いを 2 つ避ける。lint の `0 error` は「自分の変更がエラーを増やしていない」ことしか言わない（warning の内訳を変更前後で比較し既存分と新規分を切り分ける）。CI の check-runs が 0 件の状態は green ではなくワークフロー未起動である
- gem・フレームワーク・API の挙動は記憶で語らず、インストール済みのソースか一次情報で確定させる。記憶では出てこない条件（`allow_nil` を含まない `validate: true`、未知値の nil 化など）はソースを開いて初めて出る
- 引き継ぎメモ・過去の自分の記録・compaction 要約由来の数値は「当時の値」。検証や報告に使う前に実測で上書きする

## 引用・参照の作法

- 他文書・規則・ADR・先例を根拠に引く前に、必ず原文を開いて適用範囲（タイトル・冒頭・但し書きの射程宣言）を確認する。孫引き（カード・要約・記憶・語感）は「読んだ」に入らない
- この義務は逐語引用のときだけではない。**根拠として言及するだけで原文を開く義務が生じる**。他文書が挙げている参照先を自分の根拠に流用するときは、その参照先自体を開く
- 「そのもの」「〜と同じ」「〜に従う」など同一性を主張する語を書くときは、原文確認のトリガーにする
- サブエージェント・外部レビューが根拠に挙げた規則名・参照先も原文確認の対象。実在しない規則名が根拠として返ってくることがある
- WebFetch の出力は要約モデルを経由した二次情報であり原文ではない。逐語引用が必要なときは `curl -sL` で取得してタグを除去し grep する。要約ツールの出力を引用符で囲んだ瞬間に捏造になる
- 要約は適用範囲を広げ、原文より強い断定に歪む。決定の射程（何を決めて何を決めていないか）は原文で確定させる

## 修正の波及範囲

仕様変更・語の修正・事実の訂正は、その事実が書かれている全箇所を先に列挙してから着手する。列挙の観点: 同一段落内の別表現・図・要約セクション・条件で書き分けられた箇所・他ファイルからの被参照。1 箇所直して「反映済み」と報告しない。

- 列挙はリポジトリ内で閉じない。**すでに外部へ出た記述**（PR のタイトル・本文、issue 本文、投稿済みコメント）も対象に含める
- 他人の記述だけでなく、**自分がこの作業で書いた箇所**も対象。編集後に同一ファイル内の図・表・本文を同じ語で再 grep する（自分が直した図と数行下の表が矛盾する状態を自分で作った事例がある）
- 一括置換は「prefix を省略した並記」を取りこぼす（`ADR-063 / 064` の後半が残る）。置換後に残存参照を検索して 0 件を確認する工程まで含める
- 「後付けの除去処理」がコードにあるときは、根本原因がまだ生きている証拠として読む。その処理の適用範囲の外側で同じ問題が起きていないか確かめる

## コメントの抽象度

コメントはコードより一段上の抽象を説明するもの。コードと同じ抽象度の言い換えは情報量がゼロで、変更時に片方だけ古くなる二重管理を生む。判定基準は「この行を消したとき、コードから読み取れなくなる情報があるか」。無ければ消す。

- 書かない: 宣言・呼び出しの和訳（`wrap_parameters false` に「〜を無効化する」）、引数や条件の逐条説明、処理手順のなぞり
- 書く: なぜそうしたか（背景・原因・経緯）、コードに現れない制約や前提、採らなかった選択肢とその理由、読み手が気づけない副作用・波及先、根拠となる ADR・issue・PR へのリンク
- 逆に、コメントが満足に書けない・書くことが思いつかないときは、そのコードの抽象化が浅い可能性を疑う。自明なコードでも同じ状態にはなるので、断定ではなくシグナルとして扱う
- 一度書いたコメントは、その記述の前提が調査で覆ったら本文と同時に直す（[修正の波及範囲](#修正の波及範囲) の対象にコメントも含める）

## 判断への応答姿勢

ユーザーが自分の判断とその論拠を提示し、「妥当かどうか判断して」「この意見に対してどう思うか」等の形で意見を求めてきた場合は、反射的な賛同で済ませず以下の順で答える:

1. **結論の妥当性**（最終判断はそれで良いか）
2. **論拠の強い部分と弱い部分**
3. **弱い論拠があった場合、それでも結論が成立するか**（別の論拠で救えるか）

- 論拠がすべて妥当なら全面賛同でよい。その場合もどの論拠が結論を支えているかを述べる
- 判断の重さに応じて深さは調整してよい（軽い判断に 3 段フルは不要）

明示的な依頼が無くても、ユーザーが方針・設計判断とその根拠を並べて共有した場合は、短くてよいので評価コメントを添える。判断と実行依頼（「これを直して」等）が混在する場合はタスクを実行し、判断に実質的な問題があるときだけ着手前に指摘する。

理由: ユーザーは自分の推論に穴があるかを確認するために意見を求めている。反射的な同意ではフィードバックの価値がなく、意見を求めた意味がなくなる。
